# Automatic Backups Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Loft backs up its library by itself on the admin's schedule, to the admin's folder, keeping as many as the admin chooses, with Back up now, Download and Restore in Library settings.

**Architecture:** One module, `src/loft/backups.py`, carried over from Shelf's `backups.py` and widened: a backup is a zip of an online SQLite copy plus `covers/` and `uploads/`. The settings live with the other library settings (`libsettings.py`); a background `BackupKeeper` thread like `updates.UpdateChecker` makes them; admin routes in `app.py`; a panel module `web/js/backups.js` like `web/js/updates.js`.

**Tech Stack:** Python 3.14, FastAPI, sqlite3 (online backup API), zipfile; plain ES modules for the web app.

**Spec:** `docs/superpowers/specs/2026-11-21-backups-design.md`

## Global Constraints

- Backup file names: `loft-YYYY-MM-DD-HHMMSS.zip`, and `loft-YYYY-MM-DD-HHMMSS-before-restore.zip` for the copy made before a restore. Only files matching `^loft-\d{4}-\d{2}-\d{2}-\d{6}(-before-restore)?\.zip$` are ever listed, removed or restored.
- In a backup: `loft.db`, `covers/…`, `uploads/…`. Never the page cache (`cfg.page_dir`), the flow cache (`cfg.flow_dir`) or `secret_key`.
- Settings: `backup_every` ∈ {`"day"`, `"week"`, `"off"`} default `"day"`; `backup_dir` = `""` (meaning `cfg.data_dir / "backups"`) or an absolute, existing, writable folder that is not inside, and does not contain, any books folder; `backup_keep` ∈ {0, 5, 10, 30} default 0 (0 = one a day for the last 7 days, then one a week for the 8 weeks before).
- Due: daily when the newest regular backup is ≥ 23 h old; weekly when ≥ 7 days − 1 h old; off never (and prunes nothing).
- The newest regular backup is never pruned. `-before-restore` backups are outside the rule and removed after 30 days.
- A backup is written as `<name>.part` and renamed when whole.
- Admin routes only. Settings save through `PATCH /api/library`.
- Copy follows the app's voice: plain, sentence case, no apologies, curly apostrophes (’) in user-facing text.
- Commit only when the user asks (project rule): the commit steps below are where commits would go; batch them if the user asks for one commit.

## Review Focus

1. The backup folder is on a drive that isn't there (an unplugged USB disk, a sleeping NAS): the scheduled backup fails, admins get one notification, the panel says why, Loft keeps running. (Task 4: `test_a_folder_that_is_gone_fails_loudly_once`.)
2. The admin points backups at a folder that holds other files, including other zips: pruning and listing touch only Loft's backups. (Task 1: `test_only_lofts_backups_are_touched`.)
3. Restoring a zip that is damaged, not Loft's, or carries `../` paths: refused before anything changes. (Task 3: `test_bad_backups_are_refused_before_anything_changes`.)
4. A backup taken while Loft has writes not yet checkpointed (WAL): the backup holds them. (Task 1: `test_the_backup_holds_what_was_just_written`.)
5. Restoring a backup from an older Loft that lacks newer columns: Loft adds them and keeps working. (Task 3: `test_an_older_backup_gets_the_newer_columns`.)
